1. Инициализация и валидация блокчейн-цепочки
Сценарий 1.1. Создание genesis-блока при инициализации новой цепочки
Дано: в файловой системе отсутствует файл test.chain.
Когда: выполняется загрузка страницы /portal/data/ (GET-запрос).
Тогда: создаётся новый объект Chain, генерируется genesis-блок с index = 0, prev_hash из 64 нулей, и цепочка сохраняется в test.chain.
И в ответе отображается пустой список записей.

Сценарий 1.2. Валидация корректной цепочки
Дано: существует цепочка, состоящая из genesis-блока и нескольких добавленных блоков, без повреждений.
Когда: вызывается метод Chain.is_valid().
Тогда: метод возвращает True.
И для каждого блока выполняется: hash == compute_hash(), prev_hash равен хешу предыдущего блока, индексы последовательны.

Сценарий 1.3. Обнаружение повреждённого блока
Дано: в сохранённой цепочке изменён payload одного из блоков (без пересчёта хеша).
Когда: цепочка загружается через Chain.load(path) и вызывается is_valid().
Тогда: валидация возвращает False.
И при отображении на странице /portal/data/ для повреждённого блока в колонке match будет указано BROKEN.

2. Добавление медицинской записи через портал пациента
Сценарий 2.1. Успешное добавление записи
Дано: пользователь находится на странице /portal/data/, цепочка инициализирована.
Когда: пользователь отправляет POST-запрос с полями patient_name и diagnosis.
Тогда: в цепочку добавляется новый блок с типом "medical_record" и payload, содержащим переданные значения.
И цепочка сохраняется в test.chain.
И происходит редирект на ту же страницу, где новая запись отображается в таблице.

Сценарий 2.2. Проверка целостности после добавления
Дано: в цепочку только что добавлена новая запись.
Когда: страница /portal/data/ отображается повторно.
Тогда: для нового блока в колонке match отображается OK (сохранённый хеш совпадает с пересчитанным).
И в колонке prev_link отображается OK (ссылка на предыдущий блок корректна).

Сценарий 2.3. Обработка пустых полей (негативный сценарий)
Дано: пользователь отправляет POST-запрос на /portal/data/ с пустым patient_name или diagnosis.
Когда: сервер обрабатывает запрос.
Тогда: блок всё равно добавляется (текущая реализация не содержит валидации на стороне сервера), но это поведение должно быть пересмотрено: в идеале должна возвращаться ошибка валидации.
Примечание: сценарий фиксирует текущее поведение и может служить основой для доработки.

3. Интерфейс клиники
Сценарий 3.1. Отображение идентификатора и роли узла
Дано: в настройках Django заданы NODE_ID и NODE_ROLE.
Когда: выполняется GET-запрос к странице клиники (clinic/index.html).
Тогда: в контексте шаблона передаются значения node_id и node_role.
И страница корректно отображает эти данные.

4. Сохранение и загрузка цепочки
Сценарий 4.1. Сохранение цепочки в файл
Дано: в памяти существует объект Chain с несколькими блоками.
Когда: вызывается chain.save("test.chain").
Тогда: в файле test.chain создаётся JSON-представление цепочки, включающее все блоки с полями index, prev_hash, type, timestamp, payload, hash.
И при необходимости создаются родительские директории.

Сценарий 4.2. Загрузка цепочки из файла с проверкой валидности
Дано: существует корректный файл test.chain.
Когда: вызывается Chain.load("test.chain").
Тогда: возвращается объект Chain, содержимое которого соответствует файлу.
И при загрузке неявно выполняется проверка валидности: если цепочка повреждена, загрузка должна сопровождаться ошибкой или возвратом None (в зависимости от требуемой обработки).

5. Запуск и развёртывание
Сценарий 5.1. Запуск через Docker Compose
Дано: в репозитории присутствуют docker-compose.yml и docker-compose.portal.yml.
Когда: выполняется docker-compose up.
Тогда: поднимаются контейнеры с Django-приложением и необходимыми зависимостями.
И приложение доступно по указанному порту (например, портал — по /portal/, клиника — по /clinic/).

Сценарий 5.2. Применение миграций
Дано: проект развёрнут, база данных пуста.
Когда: выполняется python manage.py migrate.
Тогда: создаются все необходимые таблицы.

6. Тестовые данные и скрипты
Сценарий 6.1. Генерация узлов скриптом
Дано: в папке scripts/ присутствует generate_nodes.py.
Когда: скрипт запускается.
Тогда: генерируются тестовые данные для узлов (в соответствии с логикой скрипта), которые могут быть использованы для демонстрации или тестирования.
