## 1. Модель

**Консорциум клиник.**
- Несколько клиник — узлы сети.
- Каждая хранит **полную цепочку + все блобы** (полная репликация).
- **Список клиник — в цепочке.**
- Консенсус — большинство клиник.

**Роли (все — в цепочке):**
- **Пациент** — любой пользователь, читает своё.
- **Врач** — от клиники, пишет записи.
- **Представитель клиники** — аналог админа узла, голосует от имени клиники.

---

## 2. Ключи пациентов

**Ключ — только у пользователя.**
- При регистрации пациент генерирует пару ключей **на своём устройстве**.
- Приватный ключ **никогда не покидает устройство**.
- Публичный ключ — в цепочке (реестр пациентов).
- Врач, создавая запись, шифрует её **публичным ключом пациента**.
- Узел хранит **только зашифрованный блоб**.
- Пациент скачивает блоб и расшифровывает **у себя на устройстве**.
- Ни один узел, ни один админ — не может расшифровать.

**Что это даёт:**
- Сервер/узел не видит медицинских данных.
- Даже компрометация узла не раскрывает записи.
- Пациент — единственный владелец доступа.

**Что это меняет:**
- Узел не может отдать расшифрованные данные — только зашифрованный блоб.
- Нужен клиентский инструмент для расшифровки.
- Восстановление ключа — проблема (см. нерешённое).

---

## 3. Блокчейн

**Основа:**
- Хеш-цепочка, append-only.
- Каждый блок: `prev_hash`, `type`, `timestamp`, подписи.
- Канонизация JCS/CBOR.
- Консенсус: большинство клиник.

**Типы блоков:**

| Тип | Статус | Кто создаёт |
|---|---|---|
| `medical_record` | Реализуем | Врач |
| `patient_registry` | Реализуем | Пациент (публичный ключ) |
| `clinic_registry` | Заглушка | Представитель клиники / кворум |
| `credential` | Заглушка | Клиника |
| `credential_revocation` | Заглушка | Клиника / кворум |
| `tombstone` | Заглушка | Врач |
| `checkpoint` | Заглушка | Узел |

Поле `type` — основа расширяемости.

---

## 4. Данные

**Разделение:**
- Открытые метаданные — в блоке.
- Зашифрованный блоб — в БД на каждом узле.
- Хеш блоба — в блоке.

**Шифрование:**
- Гибридное: AES для содержимого + RSA/ECC (публичный ключ пациента).
- Расшифровка — **только на устройстве пациента**.
- Подписи врачей — неотказуемость.

**Структура `medical_record`:**
```
{
  "type": "medical_record",
  "id": "uuid",
  "patient_id": "псевдоним",
  "patient_pubkey": "...",
  "doctor_id": "...",
  "timestamp": "ISO 8601",
  "schema_version": "1.0",
  "prev_hash": "...",
  "encrypted_payload_hash": "...",
  "encrypted_payload_ref": "...",
  "doctor_signature": "..."
}
```

## 5. Идентичность

**Всё — в цепочке:**
- Клиники — реестр в цепочке.
- Врачи — привязка к клинике, в цепочке.
- Пациенты — публичный ключ в цепочке.
- Представители клиник — в цепочке, привязаны к клинике.

**Добавление/удаление клиник:**
- Заложить архитектурно.
- Реализация — позже.

---

## 6. Консенсус

- Голосование представителями клиник.
- Блок принят, если подписан большинством.
- Простой протокол, без BFT.
- Список голосующих — в цепочке.

---

## 7. Проверка

- **Утилита целостности** — пересчёт цепочки.
- **Проверка пациентом** — скачать блоб, расшифровать у себя, сверить хеш.
- **Обнаружение подмены** — расхождение цепочек между узлами.

---

## 8. Что реализуем сейчас

1. Хеш-цепочка, append-only.
2. Тип `medical_record`.
3. Тип `patient_registry` (публичные ключи).
4. Поле `type` + зарезервированные типы.
5. Канонизация JCS/CBOR.
6. Открытые метаданные + зашифрованный блоб.
7. Гибридное шифрование (AES + публичный ключ пациента).
8. Расшифровка на устройстве пациента.
9. Подписи врачей.
10. Роли в цепочке: пациент, врач, представитель клиники.
11. Реестр клиник в цепочке.
12. Несколько узлов, полная репликация.
13. Синхронизация узлов.
14. Простой консенсус (большинство).
15. Обнаружение подмены.
16. Проверка целостности.
17. Проверка пациентом (клиентский инструмент).

---

## 10. Что отложено

- BFT-консенсус.
- Распределённое хранение блобов (DHT).
- Логи/аудит.
- Break-glass.
- Восстановление ключа пациента.
- Якорение.
- Криптошреддинг.
- DID, PKI.
- HSM.

---

## 11. Что забыто

- Юридические соответствия (GDPR/152-ФЗ).
- Social recovery.
- Ротация ключей.
- Аппаратные токены.

---

## 12. Нерешённые проблемы на будущее

1. **Восстановление ключа пациента** — потеря ключа = потеря доступа.
2. Механизм добавления/удаления клиник.
3. Роль и назначение представителя клиники.
4. Креденшлы врачей.
5. Отзыв креденшлов.
6. `tombstone` — аннулирование.
7. `checkpoint` — точки сверки.
8. Merkle-доказательства.
9. Якорение.
10. Логи/аудит.
11. Break-glass.
12. Точные правила консенсуса.
13. Выход клиники — что с данными.
14. Миграция схемы.
15. Производительность.
16. UI для проверки.
17. Юридические соответствия.
18. **Экстренный доступ** — если ключ только у пациента, врач не прочитает в критической ситуации.
