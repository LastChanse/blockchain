# Техническое задание

## Информационная система хранения историй болезней на блокчейне

---

## 1. Общие сведения

**Наименование системы:** Информационная система хранения историй болезней пациентов на блокчейне.

**Назначение:** Обеспечение неизменяемого, защищённого от подмены хранения медицинских записей с разграничением прав доступа между участниками консорциума клиник.

**Область применения:** Медицинские учреждения (клиники), объединённые в консорциум, их врачи и пациенты.

---

## 2. Цели и задачи

**Цели системы:**
- Хранение историй болезней в виде неизменяемой цепочки записей (append-only).
- Обеспечение возможности добавления новых записей только в конец цепочки.
- Обнаружение подмены ранее сохранённых данных.
- Разграничение прав доступа: врачи пишут, пациенты читают только свои записи.
- Обеспечение конфиденциальности медицинских данных: доступ к содержимому есть только у пациента.

**Задачи системы:**
- Приём и сохранение медицинских записей от врачей.
- Предоставление пациенту доступа к его собственным записям.
- Поддержание целостности цепочки записей.
- Синхронизация данных между узлами консорциума.
- Предоставление инструментов проверки целостности и подлинности записей.

---

## 3. Термины и определения

| Термин | Определение |
|---|---|
| **Консорциум** | Объединение клиник, совместно управляющих сетью и хранящих данные. |
| **Узел** | Программно-аппаратный комплекс клиники-участника консорциума, хранящий полную копию цепочки и данных. |
| **Блокчейн** | Неизменяемая цепочка блоков, связанных криптографически. |
| **Блок** | Единица хранения данных в цепочке, содержащая записи определённого типа. |
| **Медицинская запись** | Запись о состоянии здоровья пациента, созданная врачом. |
| **Пациент** | Пользователь системы, которому принадлежат медицинские записи. |
| **Врач** | Пользователь системы, имеющий право создавать медицинские записи. |
| **Представитель клиники** | Пользователь, действующий от имени клиники в консорциуме (аналог администратора узла). |
| **Ключ пациента** | Криптографический ключ, позволяющий расшифровать медицинские записи. Хранится только у пациента. |
| **Полная репликация** | Хранение каждым узлом полной копии цепочки и всех данных. |

## 4. Участники системы и их роли

### 4.1. Клиника (узел консорциума)

- Является участником консорциума.
- Хранит полную копию цепочки блоков и все зашифрованные данные.
- Обеспечивает доступ пользователей к системе.
- Участвует в голосовании при принятии решений консорциума (через представителя).
- Список клиник хранится в самой цепочке.

### 4.2. Пациент

- Любой пользователь, зарегистрированный в системе.
- Имеет право:
  - Читать только свои медицинские записи.
  - Расшифровывать свои записи (ключ хранится только у него).
- Не имеет права:
  - Читать чужие записи.
  - Создавать или изменять медицинские записи.

### 4.3. Врач

- Пользователь, прикреплённый к клинике.
- Имеет право:
  - Создавать медицинские записи для пациентов.
  - Подписывать записи своим ключом.
- Не имеет права:
  - Читать записи, не относящиеся к его пациентам, без соответствующего доступа.
  - Изменять ранее созданные записи.

### 4.4. Представитель клиники

- Пользователь, действующий от имени клиники в консорциуме.
- Имеет право:
  - Голосовать от имени клиники при принятии решений консорциума.
  - Управлять узлом клиники.
- Назначается внутри клиники (вне рамок системы).

## 5. Функциональные требования

### 5.1. Управление участниками

**5.1.1. Регистрация пациента**
- Любой пользователь может зарегистрироваться в системе в роли пациента.
- При регистрации пациент генерирует пару ключей на своём устройстве.
- Приватный ключ не покидает устройство пациента.
- Публичный ключ пациента сохраняется в цепочке (реестр пациентов).

**5.1.2. Регистрация врача**
- Врач прикрепляется к клинике.
- Сведения о враче сохраняются в цепочке.
- Врач получает возможность создавать медицинские записи.

**5.1.3. Регистрация клиники**
- Клиника становится участником консорциума.
- Сведения о клинике сохраняются в цепочке.
- Список клиник доступен всем участникам.

**5.1.4. Назначение представителя клиники**
- Представитель клиники назначается внутри клиники.
- Сведения о представителе сохраняются в цепочке.

### 5.2. Работа с медицинскими записями

**5.2.1. Создание медицинской записи**
- Врач создаёт запись для пациента.
- Запись шифруется публичным ключом пациента.
- Врач подписывает запись своим ключом.
- Запись добавляется в цепочку.
- Ни один узел не может прочитать содержимое записи.

**5.2.2. Хранение медицинской записи**
- Открытые метаданные записи хранятся в блоке цепочки.
- Зашифрованное содержимое хранится отдельно.
- Хеш зашифрованного содержимого фиксируется в блоке.
- Каждый узел хранит полную копию всех данных.

**5.2.3. Чтение медицинской записи пациентом**
- Пациент запрашивает свои записи.
- Узел выдаёт зашифрованные данные.
- Пациент расшифровывает данные на своём устройстве.
- Ни узел, ни администратор не имеют доступа к расшифрованным данным.

**5.2.4. Добавление записей**
- Новые записи добавляются только в конец цепочки.
- Изменение или удаление ранее добавленных записей невозможно.

### 5.3. Обеспечение целостности

**5.3.1. Обнаружение подмены**
- Каждый блок содержит ссылку на предыдущий блок.
- Изменение любого блока нарушает целостность цепочки.
- Расхождение цепочек между узлами выявляется при синхронизации.

**5.3.2. Проверка целостности**
- Утилита проверки пересчитывает цепочку и сверяет хеши.
- Проверка может быть выполнена на любом узле.

**5.3.3. Проверка пациентом**
- Пациент может самостоятельно проверить подлинность своей записи.
- Для этого он скачивает запись, расшифровывает её и сверяет хеш с данными в цепочке.

### 5.4. Синхронизация узлов

- Каждый узел хранит полную копию цепочки и данных.
- Новые блоки рассылаются всем узлам.
- Каждый узел проверяет новый блок перед добавлением.
- При расхождении цепочек узлы синхронизируются.

### 5.5. Консенсус

- Решения консорциума принимаются голосованием представителей клиник.
- Блок считается принятым, если его подтвердило большинство клиник.
- Голосование проводится по каждому новому блоку.

---

## 6. Нефункциональные требования

### 6.1. Безопасность

- Приватный ключ пациента никогда не покидает устройство пациента.
- Медицинские данные хранятся в зашифрованном виде.
- Ни один узел не имеет доступа к расшифрованным данным.
- Подписи врачей обеспечивают неотказуемость.
- Изменение данных без нарушения целостности невозможно.

### 6.2. Надёжность

- Полная репликация данных на всех узлах.
- Отказ одного узла не приводит к потере данных.
- Целостность данных проверяется автоматически.

### 6.3. Производительность

- Система должна обеспечивать приемлемое время отклика при добавлении и чтении записей.
- Количество клиник и записей определяется в рамках проекта.

### 6.4. Расширяемость

- Архитектура должна позволять добавление новых типов блоков без изменения существующих.
- Должна быть предусмотрена возможность добавления и удаления клиник в будущем.

---

## 7. Ограничения и допущения

**Допущения:**
- Администратор одного узла не имеет доступа к другим узлам.
- Сговор большинства клиник считается невозможным.
- Все узлы консорциума доверяют друг другу в рамках проекта.
- Пациент несёт ответственность за сохранность своего приватного ключа.

**Ограничения:**
- В текущей версии не реализуются:
  - Добавление и удаление клиник (заложено архитектурно).
  - Восстановление ключа пациента при утере.
  - Экстренный доступ к записям без согласия пациента.
  - Аудит доступа к записям.
  - Аннулирование записей.
  - Юридические соответствия (GDPR, 152-ФЗ).

## 8. Сценарии использования

### 8.1. Врач создаёт медицинскую запись

1. Врач аутентифицируется в системе.
2. Врач выбирает пациента.
3. Врач вводит данные медицинской записи.
4. Система шифрует запись публичным ключом пациента.
5. Врач подписывает запись.
6. Запись добавляется в цепочку.
7. Узлы синхронизируют новый блок.

### 8.2. Пациент читает свою запись

1. Пациент аутентифицируется в системе.
2. Пациент запрашивает свои записи.
3. Узел выдаёт зашифрованные данные.
4. Пациент расшифровывает данные на своём устройстве.
5. Пациент просматривает запись.

### 8.3. Пациент проверяет подлинность записи

1. Пациент скачивает запись.
2. Пациент расшифровывает запись на своём устройстве.
3. Пациент пересчитывает хеш.
4. Пациент сверяет хеш с данными в цепочке.
5. Пациент убеждается в подлинности записи.

### 8.4. Проверка целостности цепочки

1. Утилита проверки запускается на узле.
2. Утилита пересчитывает цепочку.
3. Утилита сверяет хеши.
4. При обнаружении расхождений — сигнал тревоги.

## 9. Состав системы (высокоуровневый)

- **Узлы консорциума** — по одному на каждую клинику.
- **Клиентское приложение для врача** — создание и подпись записей.
- **Клиентское приложение для пациента** — чтение и расшифровка записей.
- **Утилита проверки целостности** — проверка цепочки.
- **Сеть синхронизации** — обмен блоками между узлами.

---

## 10. Этапы разработки (высокоуровневый)

1. **Ядро блокчейна:** хеш-цепочка, блоки, канонизация.
2. **Хранение данных:** открытые метаданные + зашифрованные блобы.
3. **Роли и доступ:** пациент, врач, представитель клиники.
4. **Шифрование:** гибридная схема, ключи пациентов.
5. **Синхронизация узлов:** полная репликация.
6. **Консенсус:** простое голосование большинством.
7. **Проверка:** утилита целостности, проверка пациентом.

---

## 11. Критерии приёмки

- Врач может создать медицинскую запись.
- Пациент может прочитать только свои записи.
- Пациент может расшифровать запись только на своём устройстве.
- Изменение ранее добавленной записи невозможно.
- Подмена данных обнаруживается.
- Несколько узлов синхронизируются.
- Проверка целостности работает.
- Пациент может самостоятельно проверить подлинность записи.
