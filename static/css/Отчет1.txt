1. Введение
Цель: Привести интерфейс в соответствие с требованиями первой итерации 
(роли врача и пациента) и улучшить UX/UI.

2. Начальное состояние
Бэкенд был готов (модели, сервисы, views), но интерфейс был «сырым»:
1) Меню ломалось (кнопка «Выйти» прыгала на новую строку).
2) Пациент видел вкладку «Узел клиники», а врач — вкладку «Портал».
3) При нажатии «Данные» пациент перекидывался в интерфейс врача.
4) Пациент не видел свои записи (баг с привязкой блока к тому, 
	кто добавил, а не к тому, о ком он).
5) После входа всех перекидывало на Портал (даже врачей).

3. Поэтапные изменения
Этап 1: Шапка сайта и Flexbox
Проблема: Ссылки съезжали.
Решение: Переписан style.css. 
Добавлен display: flex; flex-direction: column; для header.
Теперь заголовок сверху, а меню — ровно под ним в одну строку. 
Кнопка «Выйти» прижата вправо через .user-info.

Этап 2: Разделение ролей (UI)
Проблема: Гость и пациент видели лишние кнопки.
Решение: В шаблоны base.html добавлены условия 
{% if user.doctor_profile or user.is_superuser %}. 
Теперь пациент не видит «Узел клиники», а врач не видит «Портал». 
Гость не видит ни того, ни другого.

Этап 3: Редирект после входа
Проблема: Врача перекидывало на Портал.
Решение: В config/urls.py создана функция smart_login_redirect. 
Она проверяет hasattr(user, 'doctor_profile') и перенаправляет врача в клинику, 
а пациента — в портал. В settings.py изменен LOGIN_REDIRECT_URL.

Этап 4: Цветовое кодирование
Проблема: Интерфейсы были визуально одинаковыми.
Решение: Добавлены классы theme-portal и theme-clinic для <body>, 
а также portal-header и clinic-header для <header>. 
В CSS настроены синие акценты для Портала (#1e3a5f, #2e86de)
 и зеленые для Клиники (#0f5132, #10b981).

Этап 5: Исправление логики данных (Backend)
Проблема 1: Функция data в portal/views.py перенаправляла пациента в клинику (redirect("clinic-data")).
Решение 1: Заменено на render(request, "portal/data.html", 
{"records": build_records_view(request.user)}). 
Пациент остается в Портале и видит таблицу.
Проблема 2: Врач не мог добавить запись пациенту (блок привязывался к врачу).
Решение 2: В clinic/views.py добавлен поиск пациента: User.objects.get(username=patient_name). 
Теперь блок сохраняется для целевого пациента. Добавлена обработка User.DoesNotExist (безопасность).

4. Что изменено относительно бэкенда и почему
portal/views.py: Добавлена функция data, которая отдает данные в шаблон Портала. 
Почему: Чтобы пациент не покидал интерфейс Портала.

clinic/views.py: В функцию data добавлена логика поиска пациента по имени. 
Почему: Чтобы врач мог добавлять записи любому пациенту, а не только себе.

services.py: Функция build_records_view адаптирована для приема patient=None 
(чтобы врач видел все записи, а пациент — только свои).
urls.py и settings.py: Добавлен smart_login_redirect. 
Почему: Стандартный LOGIN_REDIRECT_URL не различает роли.

5. Результат
В результате проекта итерации 1 достигнуты все требования ТЗ:
Пациент входит в Портал (синий интерфейс), видит только свои записи в виде красивой таблицы с хешами. 
Не может редактировать (только читает).
Врач входит в Узел клиники (зеленый интерфейс), видит все записи, 
может добавлять новые по логину пациента, видит список пациентов.
Безопасность: Прямой заход пациента на вкладку «Врач» блокируется (403 Forbidden).
Интерфейс: Все формы, кнопки и таблицы имеют единый стиль, 
адаптированы под мобильные устройства и четко разграничены по цветам.
